# ShardForgeDB — Trace Design

**Phase 23 — Networked Node Trace API** (updated; Phase 22 wired engine traces; Phase 21 established types)

---

## Why tracing exists

ShardForgeDB is designed to be explainable at every level. The trace system exists to make that explainability concrete: every key database operation should produce a structured, human-readable step-by-step record of what actually happened at each layer of the engine.

This is not logging. Logs capture events across many operations. A trace captures the execution path of a single operation — which components were involved, in what order, for how long, and what they found.

Example: a `GET` for a key that exists in SSTable 3 but not in MemTable should produce a trace that shows:
1. MemTable checked → miss
2. Bloom filter for SSTable 1 checked → skip (key definitely not present)
3. Bloom filter for SSTable 2 checked → skip
4. Bloom filter for SSTable 3 checked → might be present
5. SSTable 3 read → hit, returned value

This trace is educational. It shows the real LSM-tree read path — the same path that makes Bloom filters valuable, the same path that compaction affects. A student or interviewer reading this trace should understand why Bloom filters skip SSTable 1 and 2, and why SSTable 3 required a disk read.

---

## Rule: traces must be generated by real execution paths

Traces must never be fabricated, pre-written, or hardcoded for display purposes.

A valid trace is one where:
- Each step is added by the actual code that performed that operation
- Duration values are real wall-clock measurements, not fixed zeros or estimates
- Step ordering matches actual execution order
- The step count reflects the actual work done (e.g., if there are 4 SSTables, there are 4 Bloom filter steps)

An invalid trace would be:
- A function that returns `[]TraceStep{...}` with hardcoded step names
- A trace where every step has duration = 0 regardless of actual time
- A trace that always shows the same steps regardless of which code path was taken

## Type overview

### `OperationType`

Identifies the high-level operation:

| Constant | Meaning |
|---|---|
| `OpGet` | Single-key lookup |
| `OpPut` | Single-key write |
| `OpDelete` | Single-key deletion |
| `OpScan` | Range scan |
| `OpVectorSearch` | k-NN vector search |
| `OpVectorInsert` | Vector insertion |
| `OpRoute` | Key routing decision (gateway/proxy) |
| `OpReplicate` | Replication push or pull |
| `OpFlush` | MemTable flush to SSTable |
| `OpCompact` | SSTable compaction |

### `Component`

Identifies which engine layer produced a step:

| Constant | Layer |
|---|---|
| `ComponentEngine` | LSM-tree engine coordinator |
| `ComponentWAL` | Write-ahead log |
| `ComponentMemTable` | In-memory write buffer |
| `ComponentSSTable` | On-disk sorted segment |
| `ComponentBloom` | Bloom filter |
| `ComponentVector` | Vector search index |
| `ComponentShard` | Sharding ring |
| `ComponentReplica` | Replication log |
| `ComponentRouter` | Client-side routing |
| `ComponentNode` | HTTP node runtime |
| `ComponentNetwork` | Network I/O |
| `ComponentCLI` | Command-line interface |

### `StepType`

Describes what happened at a step. Read-path steps:

| Constant | Meaning |
|---|---|
| `StepTypeMemTableHit` | Key found in MemTable |
| `StepTypeMemTableMiss` | Key not in MemTable; search continues |
| `StepTypeBloomSkip` | Bloom filter says key is definitely not in this SSTable |
| `StepTypeBloomCheck` | Bloom filter says key might be in this SSTable |
| `StepTypeSSTableHit` | Key found in SSTable |
| `StepTypeSSTableMiss` | Key not in SSTable despite Bloom check |
| `StepTypeNotFound` | Key not found anywhere |

Write-path steps:

| Constant | Meaning |
|---|---|
| `StepTypeWALAppend` | Record appended to WAL |
| `StepTypeMemTablePut` | Key inserted into MemTable |
| `StepTypeMemTableDelete` | Tombstone inserted into MemTable |

Vector steps:

| Constant | Meaning |
|---|---|
| `StepTypeVectorLoad` | Vectors loaded from engine into index |
| `StepTypeVectorCompute` | Distance computed between query and indexed vectors |
| `StepTypeVectorTopK` | Top-k results selected |

## What `ExplainGet` should show (Phase 15 target)

When Phase 15 wires trace into the Engine:

```go
tr, value, found, err := engine.ExplainGet(ctx, "user:1")
```

The returned trace should contain steps in this order for a key found in SSTable 2:

```
[MEMTABLE] MEMTABLE_MISS         OK       42µs   "key not in memtable"
[BLOOM]    BLOOM_SKIP             SKIPPED   1µs   "sstable=000001.sst bloom=miss"
[BLOOM]    BLOOM_CHECK            OK        1µs   "sstable=000002.sst bloom=maybe"
[SSTABLE]  SSTABLE_HIT            OK      189µs   "sstable=000002.sst offset=4096"
```

For a key found in MemTable:

```
[MEMTABLE] MEMTABLE_HIT           OK       38µs   "key found in memtable"
```

For a completely missing key (2 SSTables, Bloom skips both):

```
[MEMTABLE] MEMTABLE_MISS          OK       40µs
[BLOOM]    BLOOM_SKIP             SKIPPED   1µs   "sstable=000001.sst"
[BLOOM]    BLOOM_SKIP             SKIPPED   1µs   "sstable=000002.sst"
[ENGINE]   NOT_FOUND              OK        0µs
```

## Phase 15 integration points

The following engine methods should gain an `Explain*` variant in Phase 15:

| Phase 15 method | Returns |
|---|---|
| `engine.ExplainGet(ctx, key)` | `(*Trace, []byte, bool, error)` |
| `engine.ExplainPut(ctx, key, value)` | `(*Trace, error)` |
| `engine.ExplainDelete(ctx, key)` | `(*Trace, error)` |
| `vector.Store.ExplainSearch(ctx, query, k, metric)` | `(*Trace, []Result, error)` |

The regular (non-Explain) methods must not be modified. The Explain variants execute the exact same code path and collect trace steps as they go.

The CLI command `shardforge trace get <key>` will call `ExplainGet` and print the trace as formatted text or JSON (configurable).

## Phase 26 integration: distributed traces

In Phase 26, when a GET is routed via the proxy to a specific node, the trace should include routing steps before the engine steps:

```
[ROUTER]   RING_LOOKUP            OK       24ns   "key=user:1 node=node-2"
[NETWORK]  NODE_CALL              OK      190µs   "addr=node-2:9102"
[ENGINE]   ... (engine steps from node-2 included in trace)
```

This requires trace propagation across HTTP (trace ID in request header, partial trace in response). Phase 26 design will specify the wire format.

## What traces are NOT

- Not a logging system (traces are per-operation, not process-level)
- Not a monitoring system (traces do not replace `/metrics`)
- Not a debugging tool (traces do not expose internal state or raw values)
- Not fabricated (every step comes from a real execution path or it is invalid)
- Not always-on (Explain methods are separate; regular methods have no trace overhead)
